# Бенчмарки производительности прокси

Повторяемые бенчмарки производительности находятся в `proxy/bench_test.go` библиотеки ядра `github.com/SnishaperTeam/snishaper-core` (подключены напрямую через закреплённую в go.mod версию, отдельное клонирование не нужно). Этот документ описывает запуск, покрываемые нагрузки и статистическую методологию; цель — проверять изменения производительности сравнением бенчмарков, **никогда не делать выводов по одному запуску**.

## Запуск

```pwsh
# Все бенчмарки (-count 10 даёт выборки для benchstat; -benchmem обязателен:
# аллокации — главный сигнал регрессий плоскости данных)
go test -run '^$' -bench 'Benchmark' -benchmem -count 10 github.com/SnishaperTeam/snishaper-core/proxy/ > new.txt

# Быстрая проверка (для итераций разработки; результаты НЕ для сравнения)
go test -run '^$' -bench 'Benchmark' -benchmem -benchtime 100x github.com/SnishaperTeam/snishaper-core/proxy/
```

## Покрываемые режимы прокси и сетевые пути

Оба входа — HTTP CONNECT и SOCKS5 — и полный путь direct-режима (маршрутизация → соединение → туннельная пересылка). Режимы MITM/TLS зависят от сертификатов и TLS-стека; при изменении этих путей используйте результаты direct-режима как базу и дополнительно проверяйте вручную в реальной среде.

## Типовые нагрузки

| Бенчмарк | Нагрузка |
|----------|----------|
| `BenchmarkTunnelThroughput` | Длительные передачи (большие загрузки/выгрузки): 64 КиБ round-trip |
| `BenchmarkTunnelShortConnections` | Множество коротких соединений (API-интенсивно): создание туннеля + малая полезная нагрузка + разрыв |
| `BenchmarkTunnelConcurrent` | Много параллельных соединений: `RunParallel`, параллельные туннели с малыми round-trip |
| `BenchmarkSOCKS5ShortConnections` | Churn коротких соединений SOCKS5-клиентов |
| `BenchmarkRuleMatch/rules=100\|1000` | Стоимость решения по правилам на запрос (лёгкий/тяжёлый набор правил, горячий путь) |
| `BenchmarkRuleMatchProcess` / `BenchmarkFindProcessName` / `BenchmarkProcessNameInList` | Решения маршрутизации по приложениям и определение процессов на уровне ОС |
| `BenchmarkNormalizeHost` | Нормализация host на каждый запрос |
| `BenchmarkConnRegistryRegisterRemove` / `BenchmarkConnRegistrySnapshot` | Регистрация/снятие соединений и снимок для просмотрщика соединений (реестр заполнен, 4096 записей) |

Показатели пропускной способности и задержки берутся из времени бенчмарков (ns/op; B/op и allocs/op — показатели аллокаций; время CPU и настенное время дополнительно профилируются через `-cpuprofile`).

## Статистика (межверсионное сравнение)

Одиночные запуски сильно зависят от нагрузки на машину, температуры и политики питания. Процесс сравнения:

```pwsh
go install golang.org/x/perf/cmd/benchstat@latest

# База (до изменения) → old.txt; после изменения → new.txt (команды выше, -count 10)
benchstat old.txt new.txt
```

Критерии:

- p-value ≥ 0.05 означает **отсутствие значимой разницы** — ни регрессии, ни оптимизации.
- При значимом изменении (p < 0.05) больше 5% — проверьте, изменилось ли число аллокаций (allocs/op) в ту же сторону, прежде чем делать выводы.
- PR, связанные с производительностью, прикладывают вывод benchstat; невоспроизводимые результаты не являются критерием слияния.

## Запись окружения

Вывод бенчмарков содержит поля `goos / goarch / cpu`; сохраняйте их вместе с результатами. Обе стороны сравнения должны удовлетворять:

- Одна и та же физическая машина (или та же модель CI runner), одна и та же политика питания.
- Одна и та же версия Go (`go version`).
- Отсутствие других тяжёлых фоновых задач.

CI не запускает бенчмарки (шумные общие runner'ы делают результаты несравнимыми); сравнения выполняются на машинах разработчиков или выделенном железе.

## Известные ограничения

- Бенчмарки пропускной способности/задержки работают через loopback: они измеряют **относительные накладные расходы плоскости данных** (буферизация, трекинг, блокировки), а не абсолютную WAN-пропускную способность.
- `BenchmarkFindProcessName` на macOS включает холодный старт lsof в первой итерации; игнорируйте первый образец в benchstat или зафиксируйте число итераций через `-benchtime`.
- Бенчмарки запускаются против версии ядра, закреплённой в go.mod; после обновления ядра пересоберите базу сравнения.
