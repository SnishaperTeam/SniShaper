# Сетевой регрессионный набор тестов

Область действия, порядок запуска и ограничения сетевых регрессионных тестов этого репозитория. Цель: автоматизировать все случаи регрессии сетевого состояния, которые стабильно работают в CI без повышения прав и без реального TUN-оборудования, а остальные — задокументировать.

## Случаи, запускаемые в CI (без повышения прав)

CI-задание `tests` (`.github/workflows/build.yml`) выполняется на Windows и Ubuntu:

```pwsh
go test -race -tags with_gvisor ./...
cd frontend && npx tsc --noEmit
```

Покрытие:

| Случай | Расположение | Примечания |
| --- | --- | --- |
| Машина состояний восстановления системного прокси (повторные циклы) | `app/app_regression_test.go` | 20 циклов «включение → сбой → восстановление → корректное завершение»; учёт маркеров не должен регрессировать при смене порта |
| Восстановление после частичной настройки | там же | Остаточный маркер + системный прокси уже выключен (сценарий перезагрузки) → только очистка маркера, disable никогда не вызывается |
| Чужой прокси никогда не перезаписывается | там же | Маркер есть, но прокси указывает в другую сторону → только отчёт, без изменений |
| Повтор при ошибке прав | там же | Disable завершается ошибкой (симуляция отсутствия прав администратора) → ошибка возвращается, маркер сохраняется, повтор при следующем запуске |
| Параллельные решения (-race) | там же | 64 горутины нагружают чистое ядро принятия решений |
| Пути решений при сбое / прерванном завершении / повреждённом маркере | `app/app_recovery_test.go` | Табличные тесты: принудительное завершение, неудачный запуск, прерванное завершение, перезагрузка системы |
| Экспорт диагностики и обезличивание | `app/app_diag_export_test.go` | Маскировка чувствительных полей; сбой экспорта не влияет на работающий прокси |
| Установка обновлений, автозапуск, обновление правил | `app/*_test.go`, `internal/rulesguard`, `common`, `core` | Регрессии соответствующих модулей |

Платформенные эффекты имитируются через точки подстановки `sysproxyStatusFn` / `sysproxyDisableFn` (`app/app_system.go`): тесты никогда не изменяют реальные настройки системного прокси машины и работают только с файлами маркеров внутри `t.TempDir()`.

## Случаи, требующие повышения прав или реального оборудования (вручную)

В CI они НЕ запускаются:

| Случай | Причина | Порядок ручной проверки |
| --- | --- | --- |
| Запуск/остановка/перезапуск TUN и повторные циклы, установка и очистка маршрутов | Нужны права администратора и драйвер wintun (Windows) или `/dev/net/tun` (Linux) | Запустить GUI/CLI от администратора, переключать `tun on` / `tun off` 10+ раз, следить за `tun status` и таблицей маршрутов |
| Реальное разрешение DNS, поведение IPv4/IPv6 | Зависит от доступа в интернет и окружения провайдера | При включённом прокси выполнить `curl -k -m 15` для сайтов только с IPv4 и с IPv6; для headless-сборки Linux/WSL см. процедуру тестирования TUN в `AGENTS.md` |
| Реальная запись/восстановление системного прокси в реестре | Нужны права администратора, изменяет сеть тестовой машины | Запустить GUI от администратора, многократно переключать системный прокси, проверить восстановление реестра при выходе |
| Долгие сессии и потребление ресурсов | Неприемлемая длительность в CI | Запустить локально на 24+ часа; следить за памятью (реестр соединений ограничен 4096 записями) и CPU |

## Сетевые тесты в библиотеке ядра (snishaper-core)

Тесты уровня движка находятся в репозитории `github.com/SnishaperTeam/snishaper-core`; `go test ./...` запускает их (без повышения прав):

- `proxy/proxy_integration_test.go` — HTTP-прокси end-to-end, идемпотентность Start/Stop
- `proxy/connections_test.go` — реестр соединений: регистрация/снимок/удаление, ограничение размера, счётчики байтов
- `proxy/dnsmode_test.go` — решения о режимах DNS
- `proxy/tun_config_test.go` — валидация конфигурации TUN
- `proxy/config_migration_test.go` — совместимость миграции конфигурации
- `proxy/bench_test.go` — эталонные тесты производительности (см. `docs/benchmarks.md`)
- `netiface`, `singtun`, `sysproxy` — модульные тесты перечисления интерфейсов, TUN и платформенных реализаций системного прокси
