# Профили конфигурации

Профиль конфигурации — это **именованный снимок конфигурации** (один `settings.json` + один `rules/config.json`), сохранённый для конкретной сети или сценария использования. Этот документ описывает структуру хранения и формат экспорта для тех, кому это нужно; повседневное использование описано на вики-странице «Настройка интерфейса».

## Структура хранения

```
<каталог конфигурации>/    # Windows: %APPDATA%\snishaper, Linux/XDG: ~/.config/snishaper
└── profiles/
    ├── _active.json       # маркер активного профиля {"name": "...", "switched_at": "..."}
    ├── work/
    │   ├── settings.json  # снимок настроек профиля
    │   └── rules.json     # снимок правил профиля
    └── home/
        ├── ...
```

- **Рабочие файлы — всегда единственный источник истины во время выполнения**: `config/settings.json` и `rules/config.json` никогда не перемещаются; профили лишь копируются в них и из них при переключении. Установки, не использующие профили, никак не затрагиваются (существующие конфигурации сохраняются по построению).
- Каждый каталог профиля содержит собственные полные правила (включая режимы DNS групп сайтов), апстримы, порт и прочие настройки — изоляция по построению.
- Правила имени: буквы, цифры, иероглифы CJK, пробелы, `_` и `-`, до 64 символов; префикс `_` зарезервирован.

## Семантика переключения (безопасное поведение при активных соединениях)

1. Если прокси запущен: сначала остановить его (TUN / системный прокси / активные соединения прекращаются вместе с ним).
2. Снимок текущей рабочей конфигурации сохраняется обратно в каталог **покидаемого** профиля (несохранённые правки не теряются при переключении).
3. Два снимка целевого профиля заменяют рабочие файлы.
4. Встроенный менеджер правил и subprocess ядра перезагружают конфигурацию; порт прослушивания следует целевому профилю.
5. **Прокси никогда не перезапускается автоматически**: пользователь запускает его вручную после переключения (интерфейс сообщает об этом в диалоге подтверждения).

## Формат экспорта / импорта

Экспорт — один JSON-файл (в каталоге логов, подпапка `profile-exports/`):

```json
{
  "format": "snishaper-profile",
  "version": 1,
  "name": "work",
  "exported_at": "2026-10-30T12:00:00Z",
  "settings": { ... },
  "rules": { ... }
}
```

Перед записью импорта полезные нагрузки `settings` / `rules` записываются во временный каталог и проверяются **тем же конвейером загрузки RuleManager, что и живое сопоставление**: будущие версии конфигурации, неразбираемый JSON и не-объектные структуры отклоняются с собственными пояснениями движка, а предупреждения миграции передаются в интерфейс как есть. Проваленная проверка не записывает ни одного профиля.
